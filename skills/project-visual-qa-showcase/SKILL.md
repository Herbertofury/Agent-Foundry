# Project Visual QA Showcase



Turn real project assets/code into reproducible visual QA that both catches regressions and presents the result clearly.

## Zero-Loss composition

Treat this as a bounded visual-QA overlay on `zero-loss-chat-accelerator` and any active project/Minecraft workflow. Preserve canonical asset/source IDs, model/animation semantics already established, hashes, render/runtime IDs, last checkpoint/mutation/test, blocker, no-repeat history, still-applicable domain constraints, and exact next action.

Do not restart project discovery, source inventory, coordinate-convention research, or runtime setup merely because visual QA activates. After two unchanged waves, change strategy. Do not enumerate the entire repository/skill/asset tree when a prior complete inventory + unchanged hash already resolves the source set.

If Minecraft Dev Kit owns implementation/runtime acceptance, this skill supplies deterministic visual evidence and then returns to that preserved gate. It never downgrades a required native-client proof to a software render.

## Non-negotiable rules

- Ground previews in actual project source: textures, geometry, model hierarchy, animation data, UI state, or driving code.
- Never use image generation for deterministic project previews unless the current user message explicitly requests synthetic/generated imagery.
- Evaluate actual source curves/expressions/interpolation/pivots/parent transforms/runtime overrides; do not fake animation.
- Establish source/target coordinate semantics before conversion; never guess blanket axis/sign rules.
- Keep QA reproducible and preserve render scripts/configs when practical.
- Label deterministic renders as renders, not live runtime screenshots.
- Preserve pixel art with nearest-neighbor sampling unless intentional filtering is part of the source.
- Use correct depth/visibility ordering for 3D renders.
- Preserve the author's intended content family and provenance; do not silently discard sidecar items/blocks/heads/paintings/drops/localization/etc.
- Prefer semantic/runtime parity over blind format parity.

## Workflow

### 1. Resolve source of truth once

Use the latest canonical project source plus all upstream assets needed to judge fidelity. Retain original source beside conversions when licensing permits.

Inventory the complete upstream package only when no fresh complete inventory exists or hashes changed. Classify files as direct runtime, derived runtime, or archival/provenance. Record model hierarchy, textures/alternate layers, animation/controllers/expressions/interpolation/loop timing, item/icon/egg states, runtime animation code, variant differences, and author-intended sidecars.

For full standalone source-pack ports, read `references/standalone-source-pack-porting.md`; otherwise do not load it.

### 2. Validate conversion semantics before polish

For format ports, read `references/cross-format-model-port.md` once when coordinate/model semantics are unresolved or changed. Verify hierarchy/pivots, local offsets/axis conversion, bind rotations/order, cube geometry/deformation, UV/mirroring, animation position/rotation/scale/interpolation/timing, and alternate/charged overlays.

When a protrusion or implausible render appears, inspect hierarchy/pivot/rotation-space/parent-model/UV semantics before hiding geometry or redesigning the asset.

### 3. Solve grounded contact when relevant

For seated/lying/grounded articulated Minecraft poses, read `references/minecraft-rest-pose-ik-grounding.md`. Use a fixed known-good ground plane, world-space contact measurements, and IK-aware grounding; sample idle/tail envelopes for floor/body collisions. Do not auto-snap each preview independently to hide floating.

### 4. Render anomaly-finding views

Use a consistent camera/scale/floor/background and capture enough views to expose defects: front, three-quarter, side, back, representative animation checkpoints, and important alternate states.

Render from a versioned source hash. Do not rerender the same unchanged state merely for reassurance. After a source/model/animation mutation, rerender only views/times invalidated by that change, then run the full applicable showcase once at convergence.

### 5. Build the presentation set

A strong default package includes, when applicable:

1. per-variant static PNG card;
2. per-variant animated GIF from the real loop;
3. all-variant PNG gallery;
4. combined GIF when readable;
5. MP4 for higher-quality motion;
6. focused multi-angle/source-vs-target QA sheet for risky conversions;
7. README/verification note distinguishing deterministic renders from live captures;
8. SHA-256 manifest + reproducible ZIP.

Adapt to the project's natural output; do not build redundant formats the user does not need. For standalone conversions, include author-linked companion assets in the approval grid.

### 6. Quality gates

Read `references/quality-gates.md` before closeout. Scrub several non-obvious times in animation loops, not only frame zero.

When source channels target bones that no longer exist, do not invent geometry silently. Map to a real equivalent with documentation, preserve unused source as provenance, or mark the channel not applicable. If adding motion beyond source fidelity, regression-lock the source baseline first.

### 7. Package reproducibly

Use `scripts/bundle_showcase.py` after the showcase directory is coherent:

```bash
python scripts/bundle_showcase.py /path/to/showcase \
  --zip /path/to/Project-Visual-QA-Showcase.zip \
  --manifest /path/to/Project-Visual-QA-SHA256SUMS.txt
```

Hash in stable path order and avoid repackaging unchanged showcase bytes.

### 8. Present results cleanly

Lead with the most useful all-variant/static result when available, then compactly expose combined motion and per-variant outputs. Make risky comparison sheets prominent. State what was rendered, what source/hash drove it, what was actually runtime-captured, and what remains unverified.

## Stall-safe rendering/runtime behavior

- Reuse a complete source inventory, coordinate map, render config, and source hash until a real mutation invalidates them.
- Batch independent variant/angle renders when the renderer and resources safely permit it.
- Do not serialize identical per-variant setup steps if one shared scene/bootstrap can serve them.
- Before long render/FFmpeg/native gates, checkpoint the coherent source + render config.
- If a process can safely run detached, record exact PID/run identity and observe milestones/output files instead of repeatedly rediscovering process state.
- Do not exceed two unchanged status/milestone observations; then change evidence route or work on an independent QA item.
- A render failure with unchanged input/tool state must not be retried unchanged; classify and alter the cause/route first.

## Minecraft Bedrock -> Java specialization

For Minecraft entity ports, treat Bedrock geometry/animation/client-entity/controller files + textures as the primary reference set, preserve bone names/hierarchy where practical, compose Bedrock import semantics with Java export/runtime semantics, handle Java model-space/pivots/mirroring/resetPose carefully, reproduce source expressions rather than generic replacement motion, and judge charged geometry in its intended overlay context.

Use deterministic multi-angle/multi-time renders for conversion diagnosis, but preserve Minecraft Dev Kit's native-client gate when the defect can only exist in the real runtime.

## Output standard

Aim for release-showcase polish while answering three questions quickly: **What does each variant look like? How does it move? Is the implementation actually faithful?**
