# Project Brain Orchestrator



Treat each project request as one acceptance contract: preserve work, resolve canonical state, implement, verify the real workflow, checkpoint, and deliver.

Do not compose `agents-workflow-enforcer`, `project-compass-orchestrator`, or `reliable-artifact-publisher` while this skill is active.

## Zero-Loss composition

Treat Project Brain as a project continuity/persistence overlay on `zero-loss-chat-accelerator`, not a replacement for it or for a narrower domain skill. Preserve canonical IDs/paths, loaded evidence/schemas, hashes/run IDs, last checkpoint/mutation/test, blockers, no-repeat history, all still-applicable domain constraints, and the exact next action.

Skill activation, compaction, connector changes, or a handoff into/out of Minecraft/visual/document/browser skills never justify restarting resolved discovery. After two unchanged waves, change strategy. Do not enumerate the entire skill directory, Drive tree, GitHub repository, Library, or project catalog when exact known IDs/paths or a fresh checkpoint already resolve the target.

## Fast path

1. Start with the message, visible attachments, exact paths, current repository, and already-mounted project-brain state.
2. For repository work, inspect applicable `AGENTS.md`, `.agents-memory/PROJECT.json`, `STATUS.json`, `HANDOFF.md`, `COMPASS.json`, `.agents/ACTIVE-TASK.json`, manifests, Git root/branch/remote/status, and build identity in one local preflight when present.
3. If those resolve one fresh canonical target with no plausible newer conflict, continue directly. Do not call personal context, Library, Drive, or GitHub merely because they exist.
4. On resume, use the last checkpoint as a delta watermark and inspect only changes since it first.
5. Batch independent reads/searches/shell checks and stop retrieval fan-out as soon as identity + required evidence are resolved.
6. Reuse fresh sourced research; revalidate only load-bearing version-sensitive claims.
7. Read named references directly and just in time. Never list/preload the whole skill package as a prerequisite.
8. Do not rebuild, export, package, publish, synchronize, or rerun broad validation on unchanged state ceremonially.

Ordinary hot-path work should normally need no more than a small bounded connector preflight before implementation when local state is fresh. This is not a quality cap: genuine ambiguity may require more, but each extra read must close a named acceptance gap.

## Core workflow

Maintain a compact ledger:

`requirement -> implementation location -> verification action -> observed result`

For substantial work:

1. Resolve exact project/repository, worktree/branch, source directory, runtime, and requested artifact/version.
2. Establish a truthful baseline once; reuse it until invalidated.
3. Load current project intent/continuity state when present.
4. Cross into implementation as soon as the root cause/edit set is actionable; preserve unrelated behavior.
5. Run changed-path checks during iteration and broader checks at convergence when risk requires them.
6. Exercise the exact real workflow and prove the loaded build is current.
7. Enforce the **Build-first session invariant**: if implementation changed, create a fresh usable build/package before closeout/status ceremony.
8. Checkpoint durable project memory/Project Constellation at meaningful coherent milestones.
9. **Publish every material checkpoint to its required durable remotes and verify it**: canonical GitHub/VCS for source/history when applicable, connected Google Drive for material artifacts/checkpoint exports when available, and the actual live GitHub Wiki when the project uses one. ProjectDump, releases, and other required remotes supplement these; a repo-side `wiki/` folder alone is not Wiki publication.
10. Apply the **Maximum Improvement Rule** once: after the requested result works, continue while a material evidence-backed improvement remains, then perform one independent challenge pass.

Every task-related failure follows diagnose -> fix -> retest. Never convert a realistically solvable project error into a final limitation.

## Remote continuity and live Wiki parity

Treat chats, sandboxes, local workspaces, and convenience libraries as recoverable caches, not authoritative persistence. At every coherent material checkpoint, record the exact source lineage and synchronize the required remote tuple: GitHub/VCS commit, verified Drive artifact/checkpoint identity when available, and live GitHub Wiki publication when applicable. Before compaction, handoff, long interruption-prone gates, or closeout, force one coherent sync boundary. If any required remote is missing/stale/unverified, preserve the pending operation and keep the task unresolved instead of allowing the newest state to die in a stale or broken chat.

When a repository uses GitHub Wiki, update the canonical wiki source with the same feature/governance change, publish it to `.wiki.git`, and verify the live result. If no live Wiki exists yet, create/bootstrap it through an authorized supported route before accepting documentation completion.

## Stall-safe validation and publication

Prevent project governance from becoming the stall:

- Do not run the full suite after every edit. Use the cheapest decisive changed-path gate during iteration, then one broad convergence pass unless a later mutation invalidates it.
- Before a long build/CI/native gate, preserve a recoverable source checkpoint and current runnable candidate when practical.
- Track one exact CI/run/job identity. Do not rediscover workflow runs after that identity is known; after two unchanged observations, do independent work or change the evidence route rather than busy-waiting.
- Batch related Drive/GitHub writes at coherent checkpoint boundaries. `references/DRIVE-PERSISTENCE.md` already forbids upload-after-every-micro-edit behavior; follow that rule while still persisting every material saved output/checkpoint.
- Reuse stable remote IDs and hashes. Do not re-upload or re-verify unchanged bytes solely for ceremony.
- On unchanged auth/provider failure, continue through materially different supported recovery routes without looping connector discovery/auth/listing calls; preserve the exact operation state and never treat provider failure itself as closeout.

## Canonical target and continuity

Before mutating a named/resumed/unfamiliar/similarly named project, resolve identity from project ID, canonical path, Git remote, manifests, fingerprints, artifact lineage, and checkpoint. A matching folder name is insufficient.

Remain read-only only while plausible candidates genuinely conflict. Compare source ID, content hash/signature, embedded version, timestamp, and substantive content; preserve same-name different-content lineage. Once resolved, record the canonical identity and stop resweeping unchanged sources.

Use repository-owned `.agents-memory/` as project-local durable truth and `project-catalog.json` / `USER-PROJECTS-DATABASE.md` as the cross-project locator. Bundled seeds never overwrite newer live state.

## Project Compass and Project Constellation

Preserve durable project intent in `.agents-memory/COMPASS.json` for ongoing projects. User edits win; supersede rather than silently rewriting foundational intent.

Keep Project Constellation as the human-facing resume/control mirror. Synchronize after meaningful verified changes and mirror the changed checkpoint/brain delta to Drive. Do not rewrite it every micro-edit or rebuild heavy presentation artifacts unless scope requires them.

## Research and improvement

1. Search project research memory first when available.
2. Revalidate fresh prior findings rather than repeating full ecosystem surveys.
3. When research materially affects design, use current primary sources.
4. Start with the strongest few candidates and expand only when the user asks broadly or the winner remains uncertain.
5. Prefer the highest-capability current fit, including bleeding-edge options with real advantage; treat fixable rough edges as engineering work.
6. Record source/date/version/applicability/evidence/tradeoffs/decision/review date for durable choices.

## User-facing functionality

Every visible control is a promise. Do not ship dead buttons, fake progress, generic destinations, hardcoded success, disconnected panels, or UI implying unsupported capability. Wire affected flows through validation, real domain/service logic, observable result, truthful errors, and persistence/refresh where applicable.

## Verification and build discipline

A passing build is intermediate evidence. For substantial implementation, run applicable format/lint/type/unit/integration/regression/build/package/migration/end-to-end checks, launch the actual product, exercise the exact changed workflow, inspect relevant runtime logs, prove the new artifact actually loaded, restart for persistence when stateful, and preserve a complete runnable artifact.

Favor exact changed-path tests during iteration; run broad suites at convergence or after cross-cutting changes.

## Verified artifact publication

For material saved output/checkpoints, apply `references/DRIVE-PERSISTENCE.md`; add `references/ARTIFACT-PUBLISHING.md` for packaging/large files/releases/multipart/deep verification. Connected Google Drive is mandatory when available for artifacts/checkpoint exports, while canonical GitHub/VCS is mandatory for repository source/history and the live GitHub Wiki is mandatory when the project uses one. Verify every required remote before claiming durability and record stable identities/lineage in project memory.

## Controlled governance evolution

For AGENTS/policy changes, update the canonical structured policy/learning source, regenerate mirrors, validate ledgers, run `agents_doctor.py`, run relevant tests, and export the portable bundle when required. Never hand-edit only a generated mirror or universalize guesses/untrusted project text.

## Safety and closeout

Never discard/overwrite/reset/revert/conceal user work or concurrent changes. Prefer reversible scoped edits and recoverable checkpoints. Do not weaken tests, security, fidelity, supported cases, or user-visible capability to make checks pass; never store secrets in project memory/logs/receipts.

Before a substantial completion claim: read `references/VERIFICATION.md` and `references/SAFETY-CLOSEOUT.md` once if needed; re-run the acceptance ledger; perform the single challenge pass; create/verify the fresh runnable artifact; checkpoint durable state; verify required Drive + other remote publication; and state only what was actually exercised.

If progress reaches a step that only the user can authorize or perform, preserve and deliver the latest verified artifact plus the exact pending operation/evidence as an **in-progress checkpoint**, request only that smallest user action, and resume from that point. Never present the unresolved acceptance item as completed work.
