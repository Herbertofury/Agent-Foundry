# Minecraft Repair



Operate as a root-cause repair system, not a generic troubleshooting checklist. Preserve the modpack, features, worlds, and configuration whenever technically possible. Prefer a verified compatibility patch, update, adapter, config correction, or targeted data repair over broad removal/downgrade.

## Zero-Loss composition

Treat this skill as a bounded domain overlay on `zero-loss-chat-accelerator`. Preserve the acceptance ledger, exact target/artifact IDs, loaded logs/evidence, hashes, Repair Brain matches, run/PID IDs, last checkpoint/mutation/test, blocker, no-repeat history, still-applicable Dev Kit/project constraints, and exact next action.

Skill activation, compaction, connector changes, or returning from Minecraft Dev Kit/Visual QA never justify repeating a resolved baseline. Use single-flight reads, implementation crossing, retry-with-new-information, checkpoint-before-long-gate, and monotonic progress. After two unchanged waves, change strategy. Do not enumerate the whole Drive/Repair Brain/skill directory when an exact file ID, signature, or path is known.

## Core execution loop

1. Resolve the exact broken target and supplied inputs.
2. Perform one targeted Repair Brain lookup using the strongest known failure signature unless a fresh matching result is already in the continuity capsule.
3. Establish the factual baseline from supplied files/runtime evidence.
4. Isolate the earliest causal load-stopping or behavior-breaking root cause.
5. Verify version-sensitive claims against current primary sources only when they are load-bearing.
6. Cross into implementation: apply the narrowest complete repair to the supplied artifact/config/data.
7. Verify the repaired artifact and reproduce the original workflow when runtime access exists.
8. Pass the Repair Mark v2 completion gate for every shippable repaired mod/compatibility artifact. End this step in exactly one valid state: `embedded` or `sidecar/launcher-mapping`. If loader metadata has no `logoFile`/display-icon entry, embedding is unsafe, or signatures forbid resource mutation, **sidecar/launcher-mapping is mandatory**; never treat those conditions as permission to defer or skip the image. Run `scripts/repair_mark_gate.py` on the repair record before delivery.
9. Persist/update the repair record once the attempt reaches a coherent outcome, including Repair Mark provenance/hashes and the validated integration state for every shippable repaired artifact.
10. If this repair was a subtask of Minecraft Dev Kit, return to its preserved exact next action without re-running project discovery.

Do not stop at diagnosis while a repair is realistically possible in the available environment.

## Intake and baseline

For logs/crash reports/text configs:

- Read the complete relevant fatal context; for very large logs use `scripts/triage_log.py` to avoid serial snippet chasing.
- Resolve Minecraft version, loader/version, Java, OS, launch target, implicated mods, and terminal fatal chain.
- Separate warnings from causes by execution order and exception ownership; prefer the earliest causal exception explaining the cascade.

For JAR/ZIP mods:

- Access the exact supplied file and run `scripts/inspect_jar.py` before mutation.
- Record SHA-256, embedded loader metadata/version/dependencies, class-file versions, signatures, and relevant symbol hits.
- Never trust the filename as version authority.

For worlds/save data:

- Work on a copy unless explicitly disposable.
- Preserve unrelated `level.dat`, region/player/dimension/datapack/mod data.
- Prefer targeted NBT/region/data correction to broad deletion/regeneration.

Read `references/diagnostic-playbook.md` only when the failure family is not already resolved.

## Root-cause priority

Follow actual evidence, generally preferring: missing/duplicate dependency -> wrong game/loader/Java/build -> missing class -> method/field/descriptor binary mismatch -> Mixin/transformer failure -> registry/datapack -> side violation -> rendering/native -> network mismatch -> world/save corruption -> performance/resource exhaustion.

A warning is causal only when evidence connects it to the broken path.

## Current compatibility research

Use current primary sources only when versions/APIs/releases/present support matter: upstream source/tags/commits/issues, official Modrinth/CurseForge metadata, loader docs/changelogs, and Maven/Gradle metadata.

For API drift, prove both sides: the symbol the failing mod expects and the symbol the installed dependency actually provides. A permissive dependency range is not proof of binary compatibility.

Do not repeat broad ecosystem research after the exact expected/actual symbol pair is established.

## Repair strategy

### Compatibility identity preservation (hard default)

When repairing an existing mod, preserve its original ecosystem identity whenever safely possible. Keep the original internal mod ID, advertised mod version, display name, loader identity, namespaces, registry/resource IDs, network/protocol identifiers, mixin config names and entrypoints, public classes/fields/method descriptors/interfaces, dependency IDs/ranges, and serialized IDs unless the repair genuinely requires changing one of them. A patched filename may carry a repair suffix, but do not change internal mod ID/version merely to label the patch. Addons, dependency resolvers, configs, worlds, scripts, and compatibility layers should continue detecting the repaired artifact as the original mod/version.

Before delivery, compare repaired loader metadata against the original and verify the expected mod ID/version from the repaired artifact itself. Metadata that did not need modification should remain byte-identical. Prefer a narrow implementation patch, adapter, or compatibility shim over an identity change that would break downstream compatibility. If an identity change is unavoidable, explain exactly why, identify affected dependents/world data, and treat migration compatibility as part of the repair.

Prefer, in order of fit:

1. correct a wrong/duplicate file or version;
2. update the dependent mod to a compatible build without losing requested behavior;
3. patch the dependent mod against the installed API when narrow/proven;
4. add a small compatibility shim when safer than a brittle direct patch;
5. correct config/data/registry/side/Mixin/load-order behavior;
6. repair save/world data on a copy;
7. downgrade/remove only after higher-fidelity routes are unavailable or disproven.

Do not disable unrelated features merely to obtain a launch.

## Artifact/JAR/Mixin repair

Read `references/artifact-patching.md` before modifying a JAR/class/Mixin target. For any repaired mod JAR, compatibility JAR, or repair companion being delivered, also follow `references/repair-mark.md`: resolve the exact official CurseForge/Modrinth project artwork, apply the Repair Mark v2 red double-frame/corner/check treatment without image generation, and embed it only when marker-only diff and signature safety are proven. **Absence of `logoFile`/an embedded display-icon declaration is not a deferral condition; it forces a sidecar/launcher badge.** Signed archives, unsafe icon mutation, or launcher-external art likewise force a sidecar. A shippable repair is not closeout-complete until `scripts/repair_mark_gate.py` passes. If no trustworthy official-art basis can be established at all, keep the repair outcome partial and state the visual-identity blocker instead of silently finishing without a mark.

For narrow proven class/owner/method/descriptor/constant-pool changes, dry-run `scripts/class_utf8_patch.py` first. For every patched JAR, preserve the original, hash both, run ZIP integrity, compare entries with `scripts/jar_diff.py`, verify only intended entries changed, verify original mod ID/version and other compatibility identity still match, and verify old/new symbols structurally with `javap -verbose` or equivalent when available. When a bytecode patch changes control flow, branches, exception edges, or instruction layout, also verify StackMapTable/frame correctness; `COMPUTE_MAXS` alone does not compute frames. Prefer a branch-free equivalent when safe, otherwise compute or emit valid frames and run a JVM/class verifier before delivery.

For Mixins, resolve exact mixin class, target owner/member/descriptor/injection point/priority and competing transformer before editing. Do not blanket-disable Mixins without proving the behavior is unnecessary.

## Verification scheduling

Do not rerun the whole diagnosis stack after every edit.

- After a coherent mutation, run the cheapest decisive static/package check first.
- Re-run only evidence invalidated by that mutation.
- Launch the real instance once the candidate is coherent; rerun only after a runtime-relevant change.
- A long native process may be detached only when safe; record exact PID/run identity and observe milestones rather than busy-waiting.
- Do not exceed two unchanged status/milestone observations; then change evidence route or do independent work.

## Runtime verification

When the actual instance is accessible:

1. Launch the exact repaired instance with expected Java/loader.
2. Confirm the repaired artifact loaded by path/hash/version.
3. Reproduce the original startup/gameplay path.
4. Inspect fresh `latest.log`/crash/debug evidence.
5. Confirm the original fatal signature is gone and no new task-related fatal replaced it.
6. Restart for stateful/world fixes and verify persistence.

If runtime is initially unavailable, repair/provision the runtime, toolchain, network/cache/assets, or use a materially different supported execution route and continue toward native proof. Static/package verification may be an interim checkpoint, but when runtime proof is part of acceptance it is not final completion. If a user-only action is required, preserve the exact checkpoint and remaining runtime gate for immediate resume.

## Performance repairs

Establish correctness first, then compare equivalent settings/world/location/render distance/shaders/workload. Prefer profiler/Spark/JVM/GC/chunk/frame-time evidence. Do not improve metrics by silently reducing content, fidelity, entity counts, simulation, or user-visible features.

## Output contract

For a completed repair, lead with the root cause, what changed, repaired artifact link when produced, exact verification, any unrun runtime gate, and useful hashes. Do not bury the usable repaired file below generic troubleshooting. For every shippable repaired JAR, also deliver or link the Repair Mark v2 result. The only valid closeout states are an embedded marked icon or a verified sidecar/launcher mapping. Never use `deferred`, `not run`, missing `logoFile`, or unsafe embedding as a completed visual state. Run `scripts/repair_mark_gate.py` against the final repair record before claiming completion, and retain enough provenance to prove the artwork came from the exact official project and the visual-only marking did not alter the verified gameplay repair.
